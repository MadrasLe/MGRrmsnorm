# Qwen 2.5 3B FP16 on NVIDIA L4: MegaGemm versus vLLM

This report records the compact same-session GPU matrix completed on
2026-08-22. It replaces the older T4 comparison as the current FP16 headline
for Qwen 2.5 3B. Older measurements remain historical and are not promoted
without their raw evidence or a clean rerun.

## Result summary

Across the six measured configurations, MegaGemm reached **93.1% of vLLM's
geometric-mean output throughput**. vLLM won every row, but MegaGemm remained
within 10% in five of six configurations and within 3% in both short and medium
batch-1 configurations.

| Scenario | Batch | Requested prompt tokens | MegaGemm FP16 | vLLM FP16 | MegaGemm / vLLM | Winner |
|---|---:|---:|---:|---:|---:|---|
| Single | 1 | 128 | 37.82 tok/s | 38.81 tok/s | 97.4% | vLLM by 2.6% |
| Single | 1 | 512 | 37.39 tok/s | 38.50 tok/s | 97.1% | vLLM by 2.9% |
| Long context | 1 | 2048 | 33.68 tok/s | 36.25 tok/s | 92.9% | vLLM by 7.1% |
| Batch | 8 | 128 | 281.20 tok/s | 294.65 tok/s | 95.4% | vLLM by 4.6% |
| Batch | 8 | 512 | 244.32 tok/s | 266.24 tok/s | 91.8% | vLLM by 8.2% |
| Long context | 8 | 2048 | 155.01 tok/s | 183.78 tok/s | 84.3% | vLLM by 15.7% |

The aggregate is an unweighted geometric mean across the six matched
MegaGemm/vLLM throughput ratios. It is not a claim about unmeasured models,
GPUs, batches, context lengths, or online-serving concurrency.

## Conditions

- GPU: 1x NVIDIA L4, 23,034 MiB reported by `nvidia-smi`
- Driver: 580.82.07
- GPU state at capture: P0, 2,025-2,040 MHz SM clock, 6,251 MHz memory clock
- Model: `Qwen/Qwen2.5-3B-Instruct`
- Dtype: FP16 for both backends
- Output length: 128 tokens per request
- EOS policy: ignored, producing a fixed decode length
- Maximum sequence length: 4096
- Maximum benchmark batch: 8
- Warmup: 1
- Repetitions: 3; table values are medians
- vLLM prefix caching: disabled
- vLLM CUDA Graphs and compilation: enabled by the backend defaults
- Processes: each backend ran in a fresh child process from the same Python
  environment and Colab allocation

## Interpretation and limitations

This run supports a narrow, useful claim: on this L4/Qwen 2.5 3B FP16 compact
matrix, MegaGemm delivered near-vLLM throughput for interactive batch-1 and
short batched inference, with a larger remaining gap at batch 8 and 2048
requested prompt tokens.

It does not establish output equivalence or model quality. The throughput
harness uses greedy, fixed-length generation and records generated-token counts
and timing, not a cross-backend token-by-token correctness comparison.

The compact matrix used only three repetitions. Several MegaGemm batch-1 first
samples were slower than the following samples, consistent with shape-specific
warmup or compilation. The median remained stable, but a release-grade matrix
should use at least two warmups and five repetitions across batches 1, 2, 4,
and 8.

The source directory copied into Colab did not contain Git metadata, so the
recorded commit is `null`. The archive still captures the commands and software
environment, but the run is not tied to an immutable repository revision.
Future headline reruns should execute from a clean committed checkout.

MGX+Prophet cache-hit results are intentionally documented in
[`qwen25_l4_prophet_results_20260822.md`](qwen25_l4_prophet_results_20260822.md):
they enable cache reuse on both Prophet and vLLM and therefore answer a
different serving question from this uncached FP16 matrix.
